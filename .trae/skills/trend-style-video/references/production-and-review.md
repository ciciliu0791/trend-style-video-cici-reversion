# Lean Production and Review

## Keep selection, permission and evidence separate

Maintain three explicit facts:

- Is this reference/creative version selected, and by whom?
- Is this specific operation within spending and execution authorization?
- What has actually been inspected, and what remains unknown?

None implies the other two. An image generation allowance is not approval of an unseen reference. Human selection is not proof of motion quality. A successful render is not final acceptance.

## User-facing review contract

Use one current review entry, linked in chat and in the main project review. Put creative work first: source-informed story/camera review, images with full prompts, exact video inputs, the complete motion cut, then the inspected export. Keep technical logs linked or in appendices. Do not create a second state index or move user prose through a progress-summary refresh.

Before commissioning images, show the full story/timed storyboard and whole-film findings: source-mechanism transfer, causality/discovery, performance/emotion, geography, camera feasibility, attention/readability, sound and ending. Identify beats, revisions or justified retained choices, and what requires actual image/motion evidence. Storyboard completion is not a substitute for this review.

For each needed image or video job, expose:

1. Stable frame/shot ID, story purpose and source mechanism or original departure.
2. The selected full-resolution image or playable original; label future/missing results explicitly.
3. Entry state, action or meaningful reaction, consequence/exit, camera and joins.
4. Complete image or video prompt, including shared constraints and appended revisions; proposed and actually submitted versions kept separate.
5. Ordered reference links, roles, authority/exclusions, versions and actual supported input mode.
6. Model/provider, effective parameters, requested versus selected seconds and scoped cost/attempt allowance.
7. Single-shot/cross-shot defects, evidence, disposition and any concrete user decision.

A reuse card cites its actual source rather than inventing a prompt. Full prompts may be expandable or on a directly linked readable page; a JSON file, hash, outline or summary alone does not satisfy disclosure. Derive review and request from the same selected input data where feasible, and compare exact prompt text, input order and parameters before submission. Unknown materialization still follows the evidence rules below.

After generation retain the submitted wording and pair it with results; do not improve old text retrospectively. Preserve immutable requests/approved snapshots. Historical omissions are marked as later disclosure, not prior review. Refresh the current entry when selected inputs, edit ranges or subtitles change so old builders cannot restore obsolete versions.

Image-prompt review is visible before generation but is not another per-image spending gate. Existing selected images and matching approvals remain valid. No additional production index or media calls are required for skill maintenance.

## Execute against the shared framework

Use [project control](../../../../Skills/cinematic-project-skills-cici/references/project-control.md), its state template and read-only checker. Map develop/direct to P1/P2, prepare to P3, produce to P4, assemble to P5 and deliver to P6. Keep the current delivery scope explicit; these are internal handoffs, not additional approval gates.

After reconciling actual records, check at resume, relevant reference/script changes, keyframe review, pre-submit, creation/terminal events, edits, export and feedback. Persist attempt/ID first when it becomes available. Do not poll a full-project checker on every unchanged remote status.

Keep the state index as the source of the marked PROJECT progress/questions summary. Approved snapshots and actual execution records retain their own authority. A missing or ambiguous legacy field requires an explicit verified mapping, not a guessed approval or zero-cost entry.

Only escalate unresolved material direction, permission/scope, user-experience choices or required access/material. A Q-ID needs the question, why now, recommendation, alternatives, blocked tasks and independent next work. Resolve machine-verifiable issues yourself and reuse recorded answers. No open question is a normal state.

## Image review by exception

Classify proposed images:

| Class | Action |
|---|---|
| Adopted identity/look | Reuse unchanged; do not seek selection again |
| Required new composition/contact state | Generate within image permission; agent-check; batch for user selection |
| Actual dependent endpoint | Wait for its source/selection; show the small endpoint package when available |
| Useful improvement | Explain the uncertainty; do not block a feasible shot automatically |
| Optional exploration | Omit by default; do not spend for variety without scope |

For each new image record the question it resolves, input authority, dependent shots, quantity and retry limit. No automatic multi-angle sheets, before/after pair for every action, or polishing rounds for adopted colors.

Use a per-character constraint table before commissioning: identity, hair shape/length, hair color, ears, costume, body proportions, apparent height/position and permitted anatomy/motion. Use the selected group composition to judge apparent height, not only a numerical body-height ratio. Natural turn/tilt occlusion is not the same as an ear disappearing structurally.

Count every initial candidate and every targeted correction as an actual image request. Planned allowance, user-authorized allowance and consumed calls are different values. Existing image permission may cover the agreed work, but a stated zero-extra-call limit cannot be silently reinterpreted as permitting "repairs."

Separate source-analysis evidence frames from model conditioning images. Let unresolved identity, staging/contact or transition states determine the latter; video reference may already supply the needed motion. Do not add images just to match the number of analytical beats.

Inspect the exact input crops together, including edges, residual tags/props, eyelines and reflection direction. "Use only the expression" is a semantic instruction, not pixel isolation. A crop that removes a defect may also remove the over-shoulder relationship or action space; recheck the chosen mechanism before adopting it. Repair only material conflicts within scope.

Batch independent image work when supported and authorized. When a service can only return one image per request, disclose the separate request count; do not describe it as one multi-image call. Do not speculate on later images that require an earlier human-selected reference.

Present one numbered contact sheet, full-resolution links and per-image prompt cards. Check both individual frames and the selected set's scale, palette, eyelines, props and causal states; list defects without hiding missing images. Include acceptable candidates even if optional polish remains. If an image fails, offer the smallest repair, simpler staging or a disclosed limitation where technically feasible. Recheck affected neighbors, not adopted colors or the entire batch. Never silently substitute an unreviewed replacement.

Use the workspace's standing permission for explicitly requested image work within its scope. Quote/check required costs and obey tool confirmations, but do not invent a new per-image spending approval gate. Unplanned retries, expanded counts and model changes are not included automatically.

## Approval matrix

| Situation | Required decision |
|---|---|
| Read, analyze, plan or self-review | Proceed without generation or new spend |
| Generate requested images within standing authorization | Proceed after applicable checks; preserve visual selection |
| Ready images and exact video jobs | One combined production-package approval |
| Continue unchanged authorized batch after successful pilot | Proceed unless user reserved a pilot checkpoint |
| Pilot invalidates later input geometry | Pause dependent jobs; revise only those inputs |
| New endpoint bytes, revised prompt/reference/settings or extra paid job | Small affected-job package with exact changes and cost |
| Local trim, hold, mix or export explicitly requested | Execute within authorized scope; recheck affected timing/cues |
| Full playable cut | One coherent review with timestamped decisions and a retain/trim/postproduction/regenerate finishing plan |
| New final-quality generation stage | Obtain concrete job/specification/spend approval if not already covered |
| Final acceptance | Record the user's decision against the exact export version |

The two planned checkpoints reduce serial review; they do not cap necessary safety/creative decisions. Never waive a tool's mandatory confirmation. When another required skill has overlapping gates, map the same artifacts and real user confirmation to them instead of duplicating requests.

The two checkpoints remain the exact video package and complete-cut review, followed by acceptance of the actual export; the five deliverables are not five approval stops. Queries, downloads, internal QC, unchanged authorized batch continuation and covered review exports do not require new routine permission.

Freeze each approved package, including job IDs, exact prompts, ordered input versions/hashes, settings, job/seconds count, cost assumptions and user confirmation. A changing working document is not an immutable approved package. Store execution progress separately. Reuse approvals only for unchanged covered work.

## Input evidence before paid submission

Verify supported roles, actual input types/order, model-readable transport and capabilities before creating a task. Use an available non-billable preview when useful, obeying any tool requirement to stop after preview. Do not postpone a useful serialization check until after generation or create a paid request just to obtain evidence.

Start capability, authentication, access and price checks alongside preparation rather than after every keyframe is selected. For Drive, distinguish folder, preview and download links; record tested content type, size and hash. A same-byte move through an already authorized route does not reopen creative approval, but opening another service, changing permissions or expanding upload scope is not included automatically.

Record these facts separately:

| Evidence level | Establishes | Does not establish |
|---|---|---|
| File/link readable | The tested client can access those bytes | The generation service can fetch them |
| Client input declaration | Intended assets, roles and order are listed | Actual media content was materialized or sent |
| Inspectable serialized request | Media types/roles/content are present in the request | The backend fetched or used them as intended |
| Backend processing evidence | What the service actually acknowledges | Faithful choreography or visual quality |

A preview listing generic `asset_reference` entries with unresolved materialization is partial evidence, neither proof of successful video-reference use nor proof of omission. Protect inline media, credentials and signed URLs in diagnostic records. Unknown required capability/transport is not support; disclose and resolve material blockers before submission. Do not infer backend input use from a visually similar output.

## Stage handoffs

Use one current project index, not a separate essay for every role.

| Stage | Required output | Exit evidence |
|---|---|---|
| Develop/direct | Style map, full treatment/storyboard, whole-film findings, camera/sound progression | Required discoveries have carriers, plausible timing and explicit unresolved tests |
| Prepare | Minimal references, image/video prompt cards, dependencies and quote | Review text matches outgoing inputs; necessary selections and exact paid scope approved |
| Produce | Original takes, task records, inspection and selection notes | Required footage available or explicitly missing in assembly |
| Assemble | Playable complete cut, source ranges, synchronized available sound | Whole experience reviewed; defects and next actions identified |
| Deliver | Actual versioned export and current manifest | Export QA, remaining limitations and acceptance status recorded |

Stages overlap. Assemble available footage while other approved jobs run. Responsibility labels are review functions; do not spawn subagents unless separately authorized.

Each active stage records input version, status, next action and blocking dependency. Use `not-started`, `in-progress`, `ready-for-review`, `passed`, `blocked`, or `needs-recheck`. Do not confuse readiness with user permission.

### Internal QC disposition, not another gate

| Review finding | Decision within existing authorization |
|---|---|
| Pass for the relevant tested requirement | Continue unchanged covered work; a pilot does not establish whole-film quality |
| Repairable defect | Name the timestamp, dependency impact and smallest repair; continue affected work only if the defect does not invalidate it |
| Blocking identity, geometry or selected-mechanism failure | Stop affected dependencies, preserve independent approvals and present a bounded solution |
| Not inspected | Do not pass it; independent work or a clearly labeled review assembly may continue, but unverified critical dependencies do not proceed as proven |

These are review dispositions, not new shared-state enum values. Keep the existing check statuses and explicit evidence mappings. A real clip can be present in a draft while its quality is unresolved; mounted/downloaded/exported does not mean selected, passed or accepted. Never waive a required check simply to clear the checker.

## Generation and budget discipline

Select the model from the brief and verified service, not a source skill's default. Record generated seconds separately from selected editorial seconds. Do not spend on a draft/final ladder if approved reuse meets the stated delivery requirement.

Track reference images, video, repairs, audio and any paid render separately. Separate estimated, pending/committed, usage-derived and settled amounts. Reconcile stages of the same charge rather than adding them together. Unknown prices remain unknown. A local reserve is not a server-enforced dollar cap.

Save an attempt record before submission and task ID immediately afterward. If a submission response is lost, mark it unknown and reconcile before creating anything new. Poll the original ID after failures; if the correct local asset is already downloaded, verify it rather than downloading repeatedly.

Use the checker to distinguish upload-before-creation failure, unknown submission, active task, terminal failure and succeeded-but-not-downloaded output. Unknown creation keeps a budget/count reservation. Read-only recovery is not a new generation. A shared grant cannot offer the same remaining slot to multiple uncoordinated submissions; rerun after each persisted attempt.

A pilot tests a named uncertainty, not the entire film. Its success authorizes no new scope. Its failure does not revoke independent approved work. Do not silently simplify a required event or commission unlimited repairs.

Choose one primary question per iteration and record other simultaneous changes. A successful package with different model, prompt, composition and references supports that combined approach, not a single-factor model claim. Do not add paid A/B trials by default.

## Edit and sound as a connected timeline

Keep one editable project; preserve user changes and inspect the current timeline before editing. Save immutable exports with distinct versions rather than copying a whole source project for each adjustment.

For each used clip record source/take hash, source in/out, timeline start/duration, rate, crop and intentional holds. Maintain stable shot IDs even after reordering. A freeze must be labeled as an editorial still, not new generated motion.

Prefer scene-relative action sound cues. Derive absolute placement from scene start, source timing and playback rate; do not shift every sound blindly. Music may remain on a global grid. On a picture change, check whether cue sync, musical payoff and ending still work.

Plan a scratch music direction early. For a supplied track, inspect its real duration and musical structure when listening is available. Align a phrase/change with the key visual moment, not merely both file endpoints. Do not stretch an entire track simply to fill runtime without a creative reason.

Record music as needed, deliberately absent or awaiting a consequential decision in the initial story review. Include exact audio prompts or licensed reuse sources, cue roles, independent spending and agreed listening steps in the video package. Assemble authorized sound in the motion cut; an explicitly silent visual draft neither authorizes audio generation nor silently cancels the final sound plan. Listening checkpoints stay inside the existing reviews.

After picture lock, finish the agreed mix. Keep original audio files, conversion settings, source/license records and automation. Technical loudness/clipping checks complement listening; they do not establish a pleasant or emotionally appropriate mix. Do not invent a universal loudness target.

## Review what was delivered

Review in three passes:

1. Experience: play the complete cut with sound when possible; assess comprehension, interest, rhythm and payoff.
2. Construction: inspect action peaks, occlusions and both sides of joins; diagnose continuity and sync problems at timestamps.
3. Delivery: verify the actual exported file's duration, dimensions, fps, streams, decode, unintended gaps and destination requirements.

Record `version/time -> observation -> viewer consequence -> smallest repair -> recheck`. Distinguish user reports, observed evidence and hypotheses. Flag unperformed motion/listening checks once clearly; do not report them as passed or block unrelated verified progress.

For each unperformed critical check provide the playable file, interval, exact question, proposed reviewer and eventual evidence. Do not ask vaguely to "review everything" or close the gap with sampled frames. Compare the full experience before and after repairs, not only the repaired pixels.

Use the same selected mechanism and action-state checks from development: has the adapted behavior, meaningful stage change and intended ending registered? More motion is not by itself better causal storytelling. Treat user-reported improvement as valid experience evidence without converting it into unperformed QA passes. Praise does not authorize new generation, upscaling or publication.

Prioritize missing required actions, broken causality and identity errors before polish. Try a selected range, alternate take, supported local repair or sound adjustment when it preserves intent. Otherwise propose an affected-job regeneration package. Reinspect the repaired scene in context.

Choose retain, editorial repair, postproduction repair or new generation per affected shot. Preserve already satisfactory performances. Verify retained sources meet the locked specification or have an explicit quality exception; disclose source versus output resolution and upscaling. Formal finishing is not automatically a new generation stage. Changed paid inputs still require the affected-job package, and new results require their own QA.

If an export already exists and its source manifest still matches the current edit, verify and deliver it rather than rendering an identical file for ceremony. Otherwise export the current project. Provide the actual file and concise limitations; do not replace delivery with a preview link alone.

## Resume and learn

Resume from current project index, selected cut, open defects, pending IDs and remaining authorization. Never reconstruct approval from silence or rewrite history to appear compliant.

Close the loop after delivery: update current file/hash, task terminal status, user feedback, unresolved checks and next action in the existing index. Verify renamed files by hash. Preserve historical download paths and approved snapshots; explicitly label an editor still tied to an older version rather than presenting it as the new cut.

After delivery, record observed image-review rounds, generated/selected image counts, time to first complete motion cut, generated versus used video seconds, rework causes, spend and feedback. Label missing measurements unknown. Compare against an actual baseline with confounders noted; this workflow's existence is not evidence it improved speed or quality.
